# 基准方法说明

> **状态：草案，开跑前定稿。** 被测模型、费用上限和消融对象现在是推荐值。定稿后不再修改，要改就换一个方案编号，新旧结果不混算。
> 机器可读的部分在 [`bench/plan.toml`](https://github.com/flywhlway/flywhl-harness/blob/main/bench/plan.toml)，两边的数字由测试核对。

先写方案再跑，是为了避免看到结果之后再挑指标。

## 要回答的问题

| 编号 | 问题 | 怎么测 |
|---|---|---|
| Q1 | harness 的机制在真实模型下成不成立？ | 24 个通用场景，乘以 5 家供应商，每组 3 次 |
| Q2 | 默认开系统沙箱要付出多少代价？ | 30 个小任务，沙箱开和关配对运行，每种配置 3 次 |
| Q3 | 轨迹回放是不是真的确定？ | 把 Q1、Q2 的全部轨迹重放一遍，统计分叉数 |

## 被测版本

- 正式结果绑定 PyPI 上的确切版本，加上这个版本的提交号。容器用 `--spec 'flywhl-harness==<版本>'` 安装，别人可以装到同一份代码。
- 模型 ID、基准代码的提交号、Python 和 bubblewrap 版本、开始时间写进每次结果的 `manifest.json`。模型版本会漂移，所以结果只代表运行当天。

## 运行环境

- 一次性 Linux 容器，不挂任何宿主目录。`bench/run.sh` 用 `git archive` 打包提交过的文件来构建镜像，结果用 `docker cp` 取走。
- 容器里有真实的 bubblewrap，被测的 bash 跑在真沙箱里。
- 运行器启动时检查自己确实在容器里，并且没有多余的挂载，否则拒绝运行。
- 密钥只为这次基准创建，并在各家控制台设好额度。模型执行的命令读不到密钥：bash 子进程会剥离这类环境变量。沙箱关的配置下，命令仍可能从 `/proc` 读到父进程的环境，这也是密钥必须专用的原因。
- 原始数据不出容器。取走的是脱敏副本，发布前再扫一遍，查到疑似密钥或本机路径就不发布。

## Q1：跨供应商矩阵

场景是 `tests/live` 里只需被测模型密钥的 24 个：Agent 机制 12 个、接入层 6 个、运行时 6 个。

被测模型：

| 供应商 | 模型 |
|---|---|
| DeepSeek | `deepseek:deepseek-flash` |
| 阿里云百炼 | `dashscope:qwen3.8-flash` |
| Moonshot（Kimi） | `kimi:kimi-k2.6` |
| MiniMax | `minimax:MiniMax-M2.7` |
| OpenRouter | `openrouter:deepseek/deepseek-v4.1-flash` |

每家给出：通过率和 Wilson 95% 区间、token、缓存命中率、费用、耗时。

- 一个场景在一次试验里只有过或不过。
- 缓存命中率 = 缓存读取 ÷（未命中输入 + 缓存读取）。
- 接入层有 5 个场景不经过 Run，没有用量记录，它们的 token 和费用不计入。这几个场景各只发一两次很短的请求。

断言针对 harness 的可观测结果（工具序列、文件内容、Run 状态、事件），不针对模型的文字。所以 Q1 测的是 harness 在这家模型上能不能正常工作，不是模型的水平。

## Q2：沙箱开和关的配对消融

**配置。** A 是默认配置：`sandbox = "auto"`，出站白名单为空。B 关掉沙箱：`sandbox = "off"`。其余相同：

| 设置 | 取值 |
|---|---|
| 模型 | `deepseek:deepseek-flash`，不配降级链 |
| 单次试验上限 | 30 轮，0.20 美元，420 秒 |
| 审批 | 无人值守自动批准。`outside_sandbox` 是人工门，这时一律拒绝，模型没有办法自己走出沙箱 |

**任务。** `bench/tasks/` 下 30 个小任务，每个有固定的工作区夹具、指令和确定性的检查脚本。检查脚本在工作区之外，模型看不到。

| 分类 | 个数 | 内容 |
|---|---:|---|
| fix | 6 | 修 bug |
| feature | 5 | 加功能 |
| refactor | 3 | 重构 |
| test | 3 | 写测试、修不稳定的测试 |
| data | 4 | 数据处理 |
| repo | 3 | git 操作 |
| environment | 6 | 其中 1 个是对照，5 个沙箱敏感 |

**沙箱敏感任务**是普通开发者会做、但碰到沙箱边界的事：改 `.git/config`、装 git hook、往家目录写文件、连本机服务。A 配置下它们按设计会失败，单独列出，不做显著性检验。其余 25 个是**普通任务**。

每个任务都验证过两件事：夹具原样时检查不通过，参考答案能通过。这条校验在 CI 里跑。

**运行顺序。** 同一任务、同一试验编号的 A、B 紧挨着跑，谁先跑由固定种子决定。供应商的负载和模型版本随时间漂移，配对要尽量抵消这一点。

**分析。** 分析方法在开跑前定下：

- 主要分析：25 个普通任务，每个任务在每种配置下按 3 次的多数决算过或不过，得到 25 对结果，做精确 McNemar 检验。这回答“开沙箱会不会拖累普通任务”。
- 次要分析：全部 30 个任务做同样的检验。
- 同时报告：每种配置的通过率和 Wilson 区间；过早停止数（Run 宣称完成但检查不通过）；普通任务上每次试验 A 比 B 多用的时间的中位数；费用。

**统计功效。** 25 个任务只能看出较大的差异。精确 McNemar 检验在 p < 0.05 下，至少要 6 个任务结论相反且方向全部一致（6:0），或者 8:1 这样的比例。所以“不显著”只说明没看出来，不说明没有影响。

## Q3：回放确定性

对 Q1、Q2 的全部顶层轨迹跑确定性回放：模型输出和工具结果都来自录制，不调用模型，不执行命令。

| 录制时的结局 | 判定为确定的条件 |
|---|---|
| 完成、预算耗尽 | 每一步的上下文指纹、工具序列、最终状态、最终答案都和录制一致 |
| 被取消、崩溃后接管失败、验收多次未过 | 走不到同样的结局，只要求上下文指纹和工具序列一致 |

- 录制时从外部进来的输入（模型写的压缩摘要、人的插话、恢复说明、验收命令的结果）从轨迹里取。其余提醒由 harness 重新算出来，这正是要检查的部分。
- 子代理的轨迹嵌在父轨迹里，不单独回放。
- 出现任何分叉都按缺陷处理。

## 失败分类

每个失败都要归类，有未归类的失败时报告拒绝写入站点。

| 分类 | 含义 | 计入通过率分母 |
|---|---|---|
| 缺密钥 | 没有这家的密钥。用例跳过，不算失败 | 否 |
| 网络与环境 | 供应商故障、限流、容器环境问题 | 否 |
| 模型随机 | harness 行为正确，模型这一次没按要求做 | 是 |
| harness 缺陷 | harness 的行为不对 | 是 |
| 沙箱边界（只用于 Q2） | 沙箱按设计拦下了任务要做的事 | 是，这是要测的代价 |

归类依据写在归类记录里，和原始数据一起发布。不计入分母的失败也逐条列出。归为 harness 缺陷的，修复或记入台账。

## 费用上限

- 总额上限 50 美元，每家上限 15 美元。两个上限都写在 `bench/plan.toml` 里，由运行器执行：到上限就停，已跑完的数据保留。
- Q1 的上限在两次试验之间检查，所以最多超出一次试验的费用。Q2 逐次检查。
- 开跑前每家先跑一遍，量出单价，再确认试验次数放得下预算。
- 费用按价格表和用量估算，OpenRouter 用接口返回的实际费用。以账单为准，报告里的数字只用于比较。

## 不下哪些结论

- **不比较模型的好坏。** 24 个场景测的是 harness 的机制，场景设计也没有考虑区分模型水平。
- **不用 Q1 预测模型的长期表现。** 3 次试验只代表运行当天的模型版本。
- **不把“不显著”写成“没有影响”。**
- **不说“开沙箱损失了多少成功率”。** 沙箱敏感任务占 5/30 是我们选的，不代表日常工作里被沙箱挡住的频率。全部任务的通过率差不能这样解读，所以主要分析只看普通任务。
- **不和其他 harness 比较。** 这里没有对照实现。
- **不把任务集当作软件工程能力的基准。** 30 个小任务只用来做配对比较，绝对通过率没有外推意义。

## 复现

```bash
bench/run.sh --env-file <密钥文件> --out <结果目录> --spec 'flywhl-harness==<版本>' all
```

不需要密钥的完整彩排：脚本化模型照着参考答案执行，工具、沙箱、检查脚本、回放、脱敏、报告都是真的。

```bash
bench/run.sh --out <结果目录> rehearse
```

运行细节见 [`bench/README.md`](https://github.com/flywhlway/flywhl-harness/blob/main/bench/README.md)。
